# BoardRookie Product Specification

- 문서 상태: Draft
- 프로젝트명: BoardRookie (보드루키)
- 제품 유형: 모바일 우선 반응형 웹앱
- 목표 공개 시점: 개발 시작 후 2~3주
- 주요 사용자: 보드게임 카페에서 할 게임을 고르는 데 어려움을 느끼는 입문자

## 1. 제품 개요

### 한 줄 소개

보드게임 카페에서 우리 일행에 맞는 게임을 찾고, 복잡한 규칙을 3~5분 안에 이해해 첫 판을 시작하도록 돕는 웹앱.

### 해결하려는 문제

보드게임 카페를 방문한 입문자는 게임의 종류와 이름을 잘 모른다. 인원수와 플레이 시간, 난이도와 장르에 맞는 게임을 찾기도 어렵다. 새로운 게임을 발견하더라도 규칙이 복잡하면 플레이를 포기하고 이미 알고 있는 게임으로 돌아간다.

BoardRookie는 게임 탐색과 규칙 이해 사이의 단절을 줄인다.

### 제품 비전

보드게임 경험이 적더라도 게임을 선택하고 시작하는 과정에서 정보 부족 때문에 포기하지 않도록 한다.

## 2. 타깃 사용자

### Primary Persona

- 보드게임 경험이 적거나 거의 없는 사람
- 친구, 연인, 가족과 보드게임 카페에 방문한 사람
- 무엇을 할지 정하지 않은 채 카페에 도착한 사람
- 규칙 설명이 길거나 어려우면 새로운 게임을 포기하는 사람

### 사용 환경

- 스마트폰으로 빠르게 접속
- 게임을 고르는 데 사용할 수 있는 시간이 제한적임
- 함께 온 일행과 화면을 공유하거나 결과를 보여줄 수 있음
- 게임을 보유한 카페인지 여부가 중요함

### 핵심 사용자 시나리오

1. 사용자가 카페에 도착한다.
2. BoardRookie에 접속한다.
3. 인원수와 플레이 가능 시간, 경험 수준과 원하는 분위기를 선택한다.
4. 조건에 맞는 게임 후보 3개를 확인한다.
5. 게임별 추천 이유와 예상 소요 시간을 비교한다.
6. 하나를 선택해 쉬운 규칙 안내를 연다.
7. 준비, 차례 진행, 승리 조건을 확인한다.
8. 실제로 게임을 시작했는지 피드백을 남긴다.

## 3. 제품 목표와 비목표

### 목표

- 게임 이름을 몰라도 조건에 맞는 게임을 발견할 수 있게 한다.
- 입문자가 규칙을 이해하는 데 필요한 정보를 구조화한다.
- 공개 페이지를 통해 검색 유입이 가능한 웹 제품을 구축한다.
- 첫 커밋부터 CI와 자동화 테스트를 운영한다.
- 사용자 행동을 계측하고 실제 피드백을 바탕으로 개선한다.

### 비목표

- 모든 보드게임을 포함하는 대규모 데이터베이스 구축
- 보드게임 카페 전체의 실시간 재고 연동
- 실시간 멀티플레이 또는 게임 자체 구현
- 커뮤니티, 채팅, 친구 관계 기능
- 초기 버전의 구독 결제
- AI가 생성한 규칙을 검증 없이 제공하는 기능

## 4. 핵심 제품 원칙

### 4.1 상황부터 시작한다

사용자에게 게임 이름이나 전문 장르를 먼저 요구하지 않는다. 인원수와 시간 등 이해하기 쉬운 조건부터 선택하도록 한다.

### 4.2 복잡도와 학습 시간을 구분한다

게임의 전략적 복잡도와 규칙을 처음 배우는 데 걸리는 시간은 서로 다르다. 가능한 경우 다음 항목을 별도로 관리한다.

- 공식 또는 출처 기반 플레이 시간
- 초보자 대상 예상 규칙 설명 시간
- 초보자 적합도
- 게임을 진행할 때 필요한 경험 수준

설명 시간은 실제 측정값인지 추정치인지 구분한다.

### 4.3 정확성과 신뢰를 우선한다

인원수, 규칙, 승리 조건을 추측해 사실처럼 노출하지 않는다. 게임별 판본과 정보 출처를 기록한다.

### 4.4 로그인 없이 핵심 기능을 제공한다

게임 탐색과 규칙 확인은 비로그인 사용자도 이용할 수 있어야 한다. 로그인은 즐겨찾기 등 꼭 필요한 기능을 도입할 때만 고려한다.

### 4.5 모바일 사용을 우선한다

작은 화면에서도 조건 선택, 게임 비교, 규칙 확인이 편리해야 한다.

## 5. MVP 기능 범위

### P0: 출시 필수

- 홈 화면에서 인원수와 시간, 경험 수준과 분위기 선택
- 선택 조건에 맞는 게임 목록과 추천 이유 표시
- 게임 상세 페이지
- 단계별 쉬운 규칙 안내 페이지
- 모바일 반응형 UI
- URL 쿼리 기반 필터 상태 유지 및 공유
- 게임별 SEO 메타데이터
- Open Graph 및 공유 미리보기 설정
- sitemap.xml 및 robots.txt 설정
- GitHub Actions CI
- 핵심 퍼널 이벤트 계측
- 핵심 흐름에 대한 Playwright E2E 테스트
- 규칙 오류 또는 유용성 피드백 제출 기능

### P1: 시간 여유가 있을 때

- 즐겨찾기
- 최근 본 게임
- 필터 결과 정렬
- 규칙 섹션별 접기 및 빠른 이동
- 사용자가 추천 결과에 만족했는지 묻는 간단한 피드백
- 추천 UX에 대한 간단한 A/B 실험 1개. 트래픽이 적어 통계적 유의성은 기대하지 않는다. 실험 설계와 노출 기록을 남기고 정성 피드백과 함께 해석한다.

### 출시 이후 검토

- 규칙 관련 AI 질문과 스트리밍 답변
- 개인화 추천
- 카페별 보유 게임 데이터
- 사용자 계정 및 기기 간 즐겨찾기 동기화

## 6. 정보 구조와 URL

### 주요 화면

| 화면        | URL                      | 목적                              |
| ----------- | ------------------------ | --------------------------------- |
| 홈          | `/`                      | 사용자의 조건 선택 시작           |
| 게임 탐색   | `/games`                 | 조건에 맞는 게임 검색             |
| 게임 상세   | `/games/[slug]`          | 게임 정보와 추천 이유             |
| 규칙 안내   | `/games/[slug]/rules`    | 단계별 규칙 설명                  |
| 인원별 탐색 | `/games/players/[count]` | 인원수 기반 공개 랜딩 페이지      |
| 시간별 탐색 | `/games/time/[range]`    | 플레이 시간 기반 공개 랜딩 페이지 |

필터 상태는 `/games?players=4&maxMinutes=60&experience=beginner`처럼 쿼리 파라미터로 표현할 수 있다.

공개 랜딩 페이지는 실제로 고유한 콘텐츠와 유용성이 있는 경로만 색인 대상으로 운영한다. 필터 조합 전체를 무조건 색인하지 않는다. 게임 수가 적은 출시 초기에는 랜딩 페이지를 색인하지 않거나 공개를 미룬다.

### 게임 상세 페이지 구성

- 게임명과 대표 이미지
- 권장 인원수와 플레이 시간
- 규칙 설명 예상 시간
- 난이도와 추천 대상
- 게임의 핵심 재미
- 추천 이유
- 규칙 안내 진입 버튼
- 출처와 정보 검토일
- 규칙 오류 제보 기능

### 규칙 안내 페이지 구성

- 30초 핵심 요약
- 게임 준비
- 차례 진행
- 행동 선택과 주요 규칙
- 승리 및 종료 조건
- 초보자가 헷갈리는 점
- 원본 규칙 출처 및 판본 정보

3~5분 안에 이해한다는 것은 제품 목표이지 모든 게임에서 보장되는 학습 시간은 아니다. 게임별 설명 길이와 예상 시간을 검증한다.

## 7. 게임 추천 기준

초기 추천은 설명 가능한 규칙 기반으로 구현한다. LLM을 추천 결과의 필수 경로에 넣지 않는다.

### 필수 조건

- 선택한 인원수 범위에 맞는 게임
- 설정한 시간 범위에 맞는 게임
- 입문자 조건을 충족하는 게임

### 선호 조건

- 원하는 분위기
- 규칙 설명 예상 시간
- 초보자 적합도
- 게임 데이터의 완전성

### 결과 표시 원칙

- 추천 게임 수는 초기에는 최대 3개로 제한한다.
- 추천 이유를 사용자에게 설명한다.
- 불확실한 데이터는 확정적인 문구로 표시하지 않는다.
- 조건에 맞는 게임이 부족하면 조건을 완화할 수 있게 안내한다.
- 카페별 보유 여부를 확인하지 않았다면 보유 중이라고 표시하지 않는다.

## 8. 데이터 정책

### 초기 데이터 규모

출시 시점에는 검증된 게임 약 10개로 시작하고, 이후 15~30개로 늘린다. 데이터 수를 늘리는 것보다 기본 정보와 규칙 설명의 정확성을 우선한다.

### 게임 데이터 필드

- `id`
- `slug`
- `name`
- `nameEn` (선택)
- `minPlayers`
- `maxPlayers`
- `recommendedPlayerCounts` (선택)
- `playTimeMin`
- `playTimeMax`
- `rulesTeachTimeMin`
- `rulesTeachTimeMax`
- `difficulty`
- `genres`
- `experienceLevel`
- `description`
- `whyRecommended`
- `imageUrl` (선택)
- `imageLicense`
- `sourceUrls`
- `edition`
- `lastVerifiedAt`

### 규칙 데이터 필드

- `gameId`
- `objective`
- `setupSteps`
- `turnSteps`
- `availableActions`
- `endConditions`
- `commonConfusions`
- `sourceUrl`
- `edition`
- `reviewedAt`

### 데이터 출처 원칙

- 공식 유통사와 공식 규칙 자료를 우선 확인한다.
- 규칙 원문을 그대로 복제하지 않고 독립적으로 설명한다.
- 이미지와 외부 데이터의 재사용 권한을 별도로 확인한다.
- 확인할 수 없는 정보는 추정 또는 미확인 상태로 기록한다.
- 규칙 설명의 판본과 검토 날짜를 관리한다.

## 9. 기술 및 아키텍처 원칙

- Next.js App Router
- TypeScript strict mode
- 서버 컴포넌트 우선
- 상호작용이 필요한 곳에만 클라이언트 컴포넌트 사용
- 공개 게임 데이터는 초기에는 정적 데이터로 관리 가능
- 피드백처럼 동적으로 쌓이는 데이터가 필요할 때 Supabase 사용
- 필터는 URL과 동기화
- 입력 검증 및 추천 로직은 UI와 분리
- SEO 메타데이터는 페이지별로 정의
- JSON-LD는 페이지 내용에 맞는 타입만 적용
- 서버 비밀값을 클라이언트 번들에 포함하지 않음
- 스타일링은 Tailwind CSS와 shadcn/ui 컴포넌트 사용
- 제품 분석 도구는 PostHog 사용

## 10. 계측 설계

### 핵심 퍼널

`landing_view` -> `filter_applied` -> `game_detail_viewed` -> `rules_started` -> `game_started_feedback`

### 보조 이벤트

- `filter_reset`
- `recommendation_empty`
- `rules_section_viewed`
- `favorite_added`
- `feedback_submitted`

### 핵심 지표

- 필터 적용률
- 추천 결과에서 상세 페이지로 이동하는 비율
- 상세 페이지에서 규칙을 열어 보는 비율
- 규칙을 확인한 사용자 중 실제 게임을 시작했다고 응답한 비율
- 추천 결과 없음 비율
- 규칙 설명에 대한 긍정 또는 부정 피드백
- 재방문율

이벤트는 제품 개선을 위한 최소한의 데이터만 수집한다. 개인을 식별할 수 있는 민감한 정보는 수집하지 않는다.

## 11. 테스트 전략

### Unit Test

- 인원수 필터
- 시간 필터
- 경험 수준 필터
- 추천 이유 생성
- 빈 결과 처리
- 잘못된 쿼리 파라미터 처리

### Playwright E2E

- 홈에서 조건 선택
- 추천 결과 확인
- 게임 상세 페이지 진입
- 규칙 안내 페이지 진입
- 핵심 규칙 섹션 확인
- 피드백 제출
- 새로고침과 공유 URL에서 필터 상태 복원

### CI

모든 Pull Request에서 다음을 실행한다.

- lint
- format check
- typecheck
- unit test
- production build
- Playwright E2E

E2E에 필요한 서버 실행 및 테스트 데이터 준비를 자동화한다.

## 12. 출시 기준

- 핵심 사용자 여정이 모바일에서 동작한다.
- 게임 필터링 결과가 검증된 데이터와 일치한다.
- 핵심 규칙 설명에 출처와 판본 정보가 있다.
- 주요 페이지에 적절한 메타데이터가 있다.
- sitemap과 robots 설정을 확인했다.
- CI가 통과한다.
- 핵심 E2E 테스트가 통과한다.
- 이벤트가 중복 또는 누락 없이 수집되는지 확인했다.
- 사용자가 규칙 오류를 제보할 수 있다.
- 개인정보, 이미지 권리, 데이터 출처 관련 기본 정책을 확인했다.

## 13. 가설과 검증

### 가설 A

입문자는 게임명보다 인원수, 시간, 분위기를 기준으로 게임을 고르는 것을 더 쉽게 느낀다.

검증: 실제 사용자 테스트에서 첫 추천 결과를 확인하기까지의 시간과 어려움을 관찰한다.

### 가설 B

단계별 규칙 안내는 긴 규칙서보다 첫 플레이를 시작하는 데 도움이 된다.

검증: 규칙 이해도, 게임 시작 여부, 설명에 대한 피드백을 수집한다.

### 가설 C

공개 상세 페이지는 검색 유입의 기반이 될 수 있다.

검증: 검색엔진 인덱싱 상태, 검색 노출, 자연 검색 유입을 관찰한다. 초기 데이터가 적을 때 검색 성과를 단정하지 않는다.

## 14. MVP의 성공 정의

MVP의 성공은 게임 수나 기능 수로 판단하지 않는다.

- 실제 보드게임 입문자가 서비스를 사용한다.
- 사용자가 추천된 게임 중 하나를 선택한다.
- 사용자가 규칙 설명을 이해하고 게임을 시작했다고 응답한다.
- 사용자 피드백을 바탕으로 적어도 한 번 제품을 개선한다.
- 공개 페이지, CI, 테스트 및 계측이 실제 배포 환경에서 작동한다.

이 문서의 가설은 사용자 테스트와 운영 데이터에 따라 수정한다.
