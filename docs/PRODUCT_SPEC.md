# 꼬리질문 Product Specification

- 문서 상태: Draft
- 프로젝트명: 꼬리질문 (작업명, 영문 표기 Kkori)
- 제품 유형: 반응형 웹 SaaS, 모바일 우선
- 목표 공개 시점: AI 없는 1차 공개는 개발 시작 후 1주, MVP 공개는 3주
- 주요 사용자: 기술 면접을 준비하는 주니어 개발자

## 1. 제품 개요

### 1.1 한 줄 소개

개발자 면접에 나오는 CS와 프론트엔드 개념을 내 말로 설명하면, AI가 빠진 핵심 포인트를 짚고 꼬리 질문으로 이해를 확인하는 학습 서비스.

### 1.2 해결하려는 문제

- 면접 준비를 질문 목록과 모범 답안을 읽는 방식으로 한다. 실제 면접은 직접 설명하고 꼬리 질문에 답하는 자리라서 읽기만으로는 부족하다.
- 정리 글은 많지만 내 설명에서 무엇이 빠졌는지는 알려주지 않는다.
- 공부한 개념을 금방 잊는다. 언제 다시 볼지 관리하기도 어렵다.

### 1.3 제품 비전

개념을 아는 것과 설명할 수 있는 것의 차이를 짧은 연습의 반복으로 줄인다.

### 1.4 도메인 선정 이유

- 만든 사람이 매일 직접 쓰는 서비스여야 개선 루프가 돈다.
- 2026-10-15에 원티드에서 최소 경력 3년 이하인 웹 React, Next.js 프론트엔드 공고 150건을 분석했다. 교육 공고는 자사 도메인 경험을 우대하는 비율이 높았고, LLM 기능 경험은 도메인과 상관없이 요구됐다.
- CS는 만든 사람이 콘텐츠와 AI 판정을 직접 검증할 수 있는 과목이다.

## 2. 타깃 사용자

### 2.1 Primary Persona

- 0~3년 차 프론트엔드 개발자와 부트캠프 수료생
- 개념은 아는데 면접에서 말로 설명하다 막혀 본 사람
- 출퇴근이나 점심시간에 짧게 공부하는 사람
- 정리 글을 더 읽기보다 직접 답해 보는 연습이 필요한 사람

### 2.2 Secondary Persona

- CS 기초를 다시 공부하는 개발자
- 면접 스터디를 하는 사람. 스터디 기능은 출시 이후 검토한다.

### 2.3 사용 환경

- 모바일: 오늘의 복습, 짧은 답변, 해설 읽기
- 데스크톱: 긴 답변 작성과 꼬리 질문 답변
- 한 번에 5~15분 사용

### 2.4 핵심 사용자 시나리오

1. 검색이나 공유 링크로 질문 페이지에 들어온다.
2. 해설을 보기 전에 자기 말로 답을 쓴다.
3. 핵심 포인트별 충족 여부와 피드백을 받는다.
4. 꼬리 질문에 답한다.
5. 핵심 포인트, 해설, 출처를 확인한다.
6. 이해도를 스스로 고르면 다음 복습 날짜가 정해진다.
7. 가입하면 기록과 복습 일정이 계정에 저장된다.
8. 며칠 뒤 대시보드의 오늘의 복습에서 같은 질문에 다시 답한다.

## 3. 제품 목표와 비목표

### 목표

- 답변과 판정, 피드백과 꼬리 질문을 거쳐 복습으로 이어지는 학습 루프를 완성한다.
- 공개 질문 페이지로 검색 유입을 실험한다.
- 비회원 체험부터 가입, 무료 사용, Pro 대기 신청까지 SaaS 퍼널을 계측한다.
- 첫 커밋부터 CI와 자동 테스트를 운영한다.
- 만든 사람이 매일 쓰고 실제 사용자 피드백으로 개선한다.

### 비목표

- 음성 답변과 화상 모의 면접
- 코딩 테스트 문제와 코드 실행
- 랭킹, 커뮤니티, 답변 공유
- AI가 만든 질문이나 해설을 검수 없이 공개하는 기능
- 이력서 첨삭과 인성 면접
- MVP 단계의 실제 결제

## 4. 핵심 제품 원칙

### 4.1 먼저 설명하고 나중에 본다

핵심 포인트와 해설은 답을 제출한 뒤에 펼친다. 먼저 보고 싶은 사용자는 펼칠 수 있지만 그 비율을 계측한다.

### 4.2 판정은 사람이 쓴 기준 안에서만 한다

AI는 질문마다 사람이 쓴 핵심 포인트를 기준으로 충족 여부를 판단한다. 핵심 포인트와 해설에 없는 사실을 새로 단정하지 않는다.

### 4.3 콘텐츠는 사람이 쓰고 출처를 단다

질문과 핵심 포인트, 해설과 꼬리 질문 후보는 사람이 쓴다. 출처와 확인일을 함께 기록한다.

### 4.4 AI가 없어도 학습이 이어진다

AI 호출이 실패하거나 사용량이 끝나면 핵심 포인트 자가 점검으로 넘어간다. 학습 루프는 끝까지 간다.

### 4.5 로그인 없이 시작하고 가입하면 이어간다

질문 열람과 체험은 비회원도 할 수 있다. 기록 저장과 기기 간 복습 일정은 가입 후 제공한다.

### 4.6 점수 대신 빠진 포인트를 보여준다

100점 만점 같은 정밀해 보이는 점수를 만들지 않는다. 충족한 포인트 수와 빠진 포인트를 보여준다.

- 웹 공개 페이지라서 검색과 링크 공유로 들어올 수 있다.

## 6. 요금제와 사용량

AI 사용량은 시도 단위로 센다. 시도 하나에는 판정, 피드백, 그 시도의 꼬리 질문이 모두 들어간다.

| 항목                       | 비회원           | Free        | Pro                   |
| -------------------------- | ---------------- | ----------- | --------------------- |
| 질문 열람, 해설, 자가 점검 | 가능             | 가능        | 가능                  |
| AI 피드백 시도             | 하루 3회         | 하루 10회   | 하루 50회             |
| 시도당 꼬리 질문           | 1개              | 2개         | 3개                   |
| 기록과 복습 일정           | 이 기기에만 저장 | 계정에 저장 | 계정에 저장           |
| 가격                       | 무료             | 무료        | MVP에서는 대기 신청만 |

- 숫자는 초기값이다. 2주 차에 시도당 토큰과 비용을 잰 뒤 확정한다.
- MVP의 Pro는 요금제 페이지와 대기 신청 버튼만 둔다. 클릭과 신청 수로 지불 의향을 본다.
- P1에서 토스페이먼츠 테스트 모드로 구독 결제를 붙인다. 계약 없이 정기 결제를 테스트할 수 있는지는 확인이 필요하다.
- 전체 일일 AI 예산 상한을 둔다. 넘으면 모든 사용자를 자가 점검으로 돌린다.

## 7. MVP 범위

### P0: MVP 공개 필수

1. 질문 콘텐츠: 카테고리마다 3개 이상, 전체 21개 이상. 스키마 검증을 포함한다.
2. 공개 페이지: 8.1의 화면 전부
3. SEO: 페이지별 메타데이터와 canonical, OG 이미지, sitemap과 robots
4. 연습 패널: 답변 입력과 핵심 포인트 판정, 피드백 스트리밍, 해설 펼치기와 자가 평가
5. 꼬리 질문: 사람이 쓴 후보에서 고르고 AI가 다듬어 묻는다. 답변도 판정한다.
6. 자가 점검 모드: AI 실패, 사용량 소진, 킬 스위치 상황에서 동작
7. 간격 반복: 다음 복습 날짜 계산과 오늘의 복습 목록
8. 계정: GitHub 로그인, 이 기기의 기록을 계정으로 합치기, 계정 삭제
9. 대시보드: 오늘의 복습과 최근 시도, 카테고리별 빠진 포인트와 남은 AI 사용량
10. 요금제 페이지와 Pro 대기 신청
11. 사용량 제한: 요금제별 제한, IP별 제한, 전체 예산 상한
12. AI 판정 신고
13. 계측: 학습 퍼널과 SaaS 퍼널 이벤트
14. CI: 콘텐츠 검증과 단위 테스트, LLM을 모킹한 E2E

### P1: 3주 안에 여유가 있으면

- 토스페이먼츠 테스트 모드 구독 결제와 Pro 사용량 적용
- 피드백 형식 A/B 실험
- 카카오 로그인
- 학습한 날 기록
- 질문 30개 채우기
- 코드 블록 구문 강조

### 출시 이후 검토

- 스터디 그룹: 같은 질문 세트로 연습하고 진도를 공유한다. B2B 확장 후보다.
- 영어 작문 질문 세트
- 사용자가 직접 만드는 질문
- 음성 답변

## 8. 정보 구조와 URL

### 8.1 공개 페이지

색인 대상이다. 모두 빌드 때 정적으로 만든다.

| 화면              | URL                      | 목적                                           |
| ----------------- | ------------------------ | ---------------------------------------------- |
| 홈                | `/`                      | 서비스 소개와 시작 질문, 이 기기의 오늘의 복습 |
| 질문 목록         | `/questions`             | 카테고리별 전체 질문                           |
| 카테고리          | `/categories/[category]` | 카테고리 랜딩                                  |
| 질문 상세         | `/questions/[slug]`      | 질문, 연습 패널, 핵심 포인트와 해설            |
| 요금제            | `/pricing`               | 요금제 비교와 Pro 대기 신청                    |
| 소개              | `/about`                 | 콘텐츠 원칙과 AI 판정의 한계                   |
| 개인정보 처리방침 | `/privacy`               | 저장 항목, 보관 기간, AI 제공자 전송           |

### 8.2 앱 페이지

색인하지 않는다. 로그인이 필요하고 요청 때 렌더링한다.

| 화면     | URL                   | 목적                                               |
| -------- | --------------------- | -------------------------------------------------- |
| 로그인   | `/login`              | GitHub 로그인                                      |
| 대시보드 | `/dashboard`          | 오늘의 복습과 최근 시도, 빠진 포인트와 남은 사용량 |
| 복습     | `/dashboard/review`   | 오늘 복습할 질문을 차례로 풀기                     |
| 기록     | `/dashboard/history`  | 지난 시도와 판정                                   |
| 설정     | `/dashboard/settings` | 요금제와 계정 삭제                                 |

### 8.3 서버 엔드포인트

AI 응답은 스트리밍이 필요해서 Route Handler로 만든다. 단순 저장은 Server Action으로 만든다.

| 종류          | 경로 또는 이름                                      | 역할                                     |
| ------------- | --------------------------------------------------- | ---------------------------------------- |
| Route Handler | `POST /api/attempts`                                | 시도 생성, 사용량 차감, 핵심 포인트 판정 |
| Route Handler | `POST /api/attempts/[id]/feedback`                  | 피드백 스트리밍                          |
| Route Handler | `POST /api/attempts/[id]/follow-ups`                | 다음 꼬리 질문 스트리밍                  |
| Route Handler | `POST /api/attempts/[id]/follow-ups/[index]/answer` | 꼬리 질문 답변 판정                      |
| Server Action | `rateAttempt`                                       | 자가 평가 저장과 복습 일정 갱신          |
| Server Action | `reportJudgment`                                    | AI 판정 신고                             |
| Server Action | `joinProWaitlist`                                   | Pro 대기 신청                            |

### 8.4 색인 정책

- `/dashboard`, `/login`, `/api`는 robots에서 막고 `noindex`를 단다.
- 카테고리는 쿼리 문자열이 아니라 경로로 만든다.
- 질문 slug는 공개 후 바꾸지 않는다. 바꿔야 하면 리다이렉트를 둔다.

## 9. 학습 흐름 상세

### 9.1 질문 상세 화면

- 질문 문장, 카테고리, 난이도
- 연습 패널. 이 부분만 클라이언트 컴포넌트다.
- 핵심 포인트와 해설. 서버에서 렌더링하고 `<details>`로 접어 둔다. 제출하면 펼친다.
- 출처와 확인일
- 관련 질문

### 9.2 연습 패널 상태

| 상태           | 화면                                                |
| -------------- | --------------------------------------------------- |
| 입력           | 답변 입력란과 글자 수, 남은 AI 사용량, 제출 버튼    |
| 판정 중        | 핵심 포인트 자리에 로딩 표시                        |
| 판정 완료      | 포인트별 충족, 부분 충족, 빠짐과 답변 속 근거 문장  |
| 피드백 작성 중 | 스트리밍되는 피드백과 취소 버튼                     |
| 꼬리 질문      | 질문, 답변 입력, 판정 결과                          |
| 자가 평가      | 다시, 애매함, 알았음 버튼과 다음 복습 날짜          |
| 자가 점검      | AI 없이 핵심 포인트를 스스로 체크                   |
| 오류           | 원인, 다시 시도, 자가 점검으로 전환                 |
| 사용량 소진    | 남은 사용량 안내, 가입이나 Pro 대기 신청, 자가 점검 |

### 9.3 입력 규칙

- 답변은 20자 이상 2,000자 이하로 받는다. 짧으면 제출을 막고 이유를 보여준다.
- 제출 전 답변은 이 기기에 임시 저장한다.
- 데스크톱에서는 Ctrl+Enter로 제출한다.

### 9.4 판정 표시 규칙

- 상태를 색으로만 구분하지 않는다. 아이콘과 문구를 같이 쓴다.
- 근거 문장은 답변에 실제로 있는 문장만 보여준다.
- 판정 아래에 AI 판정이 틀릴 수 있다는 안내와 신고 버튼을 둔다.
- 필수 포인트가 빠졌는데 알았음을 고르면 한 번 더 묻는다.

## 10. 콘텐츠 모델과 작성 원칙

### 10.1 카테고리

| ID               | 이름         | 예시 주제                         |
| ---------------- | ------------ | --------------------------------- |
| `browser`        | 브라우저     | 렌더링 과정, 이벤트 루프          |
| `javascript`     | JavaScript   | 클로저, 프로토타입                |
| `react`          | React        | 리렌더링 조건, 상태 업데이트 배치 |
| `network`        | 네트워크     | HTTP 캐시, CORS, TCP 연결         |
| `os`             | 운영체제     | 프로세스와 스레드, 교착 상태      |
| `data-structure` | 자료구조     | 해시 테이블, 힙                   |
| `database`       | 데이터베이스 | 인덱스, 트랜잭션 격리 수준        |

### 10.2 질문 필드

| 필드           | 내용                                                                  |
| -------------- | --------------------------------------------------------------------- |
| `slug`         | URL에 쓰는 고유 ID                                                    |
| `title`        | 질문 문장                                                             |
| `category`     | 10.1의 ID                                                             |
| `level`        | `basic` 또는 `advanced`                                               |
| `keyPoints`    | 3~5개. 항목마다 `id`와 `label`, `criteria`와 `required`               |
| `followUps`    | 2~3개. 항목마다 `id`와 `question`, `keyPoints`와 `relatedKeyPointIds` |
| `explanation`  | Markdown 해설                                                         |
| `sources`      | 항목마다 `title`과 `url`, `checkedAt`                                 |
| `relatedSlugs` | 관련 질문                                                             |
| `reviewedAt`   | 마지막 검토일                                                         |
| `status`       | `draft` 또는 `published`                                              |

- `label`은 화면에 보이는 짧은 이름이다. `criteria`는 AI가 판정에 쓰는 기준 문장이다.
- `required`가 false인 포인트는 보너스로 표시한다.

### 10.3 저장 방식

- 질문 하나를 `src/content/questions/<slug>.ts` 파일 하나로 둔다.
- `src/content/schema.ts`의 Zod 스키마로 검증한다. 검증은 단위 테스트로 CI에서 돈다.
- 해설은 Markdown 문자열로 쓰고 `react-markdown`으로 렌더링한다. 콘텐츠용 의존성은 이것 하나만 추가한다.
- DB에 넣지 않고 버전 관리한다. 콘텐츠 변경 이력이 곧 검토 이력이다.

### 10.4 작성 원칙

- 해설은 직접 쓴다. 블로그, 책, 다른 면접 질문 모음의 문장을 옮기지 않는다.
- 출처는 공식 문서와 표준을 먼저 찾는다. MDN과 WHATWG 표준, React 공식 문서와 RFC가 우선이다.
- 핵심 포인트는 면접관이 들으면 이해했다고 판단할 최소 기준으로 쓴다.
- `criteria`는 답변에서 확인할 수 있는 문장으로 쓴다. 예: 콜 스택이 비면 태스크 큐에서 다음 작업을 꺼낸다고 설명한다.
- 꼬리 질문은 실제 면접에서 이어질 만한 것으로 쓴다.
- 공개 전에 출처 링크를 열어 확인하고 확인일을 적는다. 가능하면 다른 개발자 한 명이 검토한다.
- 판정 신고로 오류가 확인되면 고치고 `reviewedAt`을 갱신한다.

### 10.5 공개 기준

- 1차 공개: published 질문 10개
- MVP 공개: 카테고리마다 3개 이상, 전체 21개 이상
- 목표: 30개

## 11. AI 설계

### 11.1 AI가 하는 일과 하지 않는 일

| 하는 일                                       | 하지 않는 일                                       |
| --------------------------------------------- | -------------------------------------------------- |
| 핵심 포인트별 충족 여부와 근거 문장 판정      | 질문, 핵심 포인트, 해설 생성                       |
| 판정 결과를 바탕으로 짧은 피드백 작성         | 핵심 포인트와 해설 밖의 사실 단정                  |
| 사람이 쓴 꼬리 질문을 답변 흐름에 맞게 다듬기 | 점수 매기기                                        |
| 꼬리 질문 답변 판정                           | 복습 일정, 사용량, 꼬리 질문 선택 같은 결정적 계산 |

### 11.2 호출 단계

1. 판정: 서버가 질문의 핵심 포인트를 콘텐츠에서 읽는다. 클라이언트가 보낸 기준은 쓰지 않는다. 구조화 출력으로 포인트별 `status`, `evidence`와 기준과 어긋나는 진술 목록을 받는다.
2. 피드백: 판정 결과와 해설을 넣고 3~5문장의 피드백을 스트리밍한다. 빠진 필수 포인트부터 다룬다.
3. 꼬리 질문: 코드가 후보를 고른다(11.5). AI는 사용자 답변에 이어지도록 문장을 다듬어 스트리밍한다.
4. 꼬리 질문 판정: 후보의 핵심 포인트로 1단계와 같은 판정을 하고 한 문장 코멘트를 붙인다.

`status`는 `covered`, `partial`, `missing` 중 하나다.

### 11.3 출력 검증

- 구조화 출력 결과를 서버에서 Zod로 다시 검증한다.
- 모르는 핵심 포인트 ID는 버린다. 결과에 없는 포인트는 `missing`으로 채운다.
- `evidence`가 답변에 그대로 있는 문자열이 아니면 지운다. 공백만 정규화해서 비교한다.
- 검증이 두 번 실패하면 자가 점검으로 넘긴다.

### 11.4 프롬프트 원칙

- 고정 시스템 프롬프트에 역할과 판정 규칙, 출력 형식과 금지 사항을 둔다. 질문별 내용은 그 뒤에 둔다.
- 사용자 답변은 구분자 안에 넣고 데이터로만 다루라고 명시한다. 답변 속 지시는 따르지 않는다.
- 피드백은 존댓말로 쓴다. 해설에 없는 사실은 쓰지 않는다.
- 프롬프트는 `src/lib/llm/prompts.ts`에 버전 문자열과 함께 둔다. 시도 기록과 이벤트에 프롬프트 버전을 남긴다.

### 11.5 꼬리 질문 선택 규칙

1. 빠지거나 부분 충족한 필수 포인트와 연결된 후보를 먼저 고른다.
2. 없으면 아직 묻지 않은 후보 중 첫 번째를 고른다.
3. 요금제별 최대 개수에 닿으면 더 묻지 않는다. 개수는 서버의 시도 기록으로 센다.

### 11.6 모델과 호출 설정

- 제공자는 Claude API다. `@anthropic-ai/sdk`를 서버에서만 쓴다.
- 기본 모델은 `claude-opus-5-5`다. 이 모델은 thinking을 끌 수 없어서 `output_config.effort`로 조절한다. `low`에서 시작해 품질 평가 세트 결과를 보고 올린다.
- 판정은 `messages.parse`와 `output_config.format`으로 구조화 출력을 받는다. 이 모델은 assistant prefill과 강제 `tool_choice`를 거부하므로 쓰지 않는다.
- 피드백과 꼬리 질문은 `messages.stream`으로 받아 텍스트 조각만 클라이언트로 보낸다. thinking 때문에 첫 글자 전에 대기가 생길 수 있어서 작성 중 상태를 먼저 보여준다.
- `stop_reason`을 확인한다. `refusal`이면 자가 점검으로 넘긴다. 서버 측 fallback 옵션도 켠다.
- 시간 제한은 판정 15초, 스트림 30초다. SDK 기본 재시도 2회를 그대로 쓴다.
- 사용자가 취소하면 클라이언트가 요청을 끊는다. 서버는 요청의 abort 신호로 모델 호출을 멈춘다.
- 고정 시스템 프롬프트에 캐시를 건다. 이 모델의 최소 캐시 길이는 512토큰이다. 효과는 응답의 `usage.cache_read_input_tokens`로 확인한다.
- 모델 정보는 2026-10-06 기준 Claude API 문서를 따랐다. 구현할 때 공식 문서로 다시 확인한다.

### 11.7 모의 모드와 킬 스위치

- `LLM_MODE=mock`이면 고정 응답을 돌려준다. E2E와 로컬 개발은 이 모드로 돌아서 실제 API를 부르지 않는다.
- 모의 응답에는 정상과 부분 충족, 오류와 거절 사례를 둔다.
- `AI_ENABLED=false`면 모든 AI 기능을 끄고 자가 점검만 남긴다.

### 11.8 품질 평가 세트

- 질문 10개에 대해 좋은 답, 부분 답, 틀린 답을 하나씩 만든다. 30개 사례마다 기대 판정을 적는다.
- `evals/judge/`에 두고 `npm run eval:judge`로 돌린다. 실제 API를 부르므로 CI가 아니라 수동으로 돌린다.
- 프롬프트나 모델을 바꿀 때마다 포인트별 일치율을 비교하고 결과를 PR에 적는다.

### 11.9 비용 기록

- 호출마다 모델과 토큰 수, 지연 시간과 결과 상태를 `llm_calls`에 남긴다. 토큰 수는 입력, 출력, 캐시 읽기로 나눠 적는다.
- 기록은 `after()`로 응답이 끝난 뒤에 쓴다.
- 일일 비용 합계를 예산 상한과 비교한다.

## 12. 간격 반복 규칙

- 상자는 5개이고 간격은 1, 3, 7, 14, 30일이다.
- 자가 평가에 따라 상자를 옮긴다.
  - 다시: 1번 상자
  - 애매함: 지금 상자 유지
  - 알았음: 다음 상자. 5번이면 유지한다.
- 처음 푼 질문은 다시와 애매함이면 1번, 알았음이면 2번 상자에서 시작한다.
- 다음 복습일은 평가한 날짜에 상자 간격을 더한 날이다. 날짜는 Asia/Seoul 기준이다.
- AI 판정은 일정에 직접 쓰지 않는다. 일정은 학습자의 자가 평가로만 정한다.
- `src/lib/practice/srs.ts`의 순수 함수로 만들고 경계값을 단위 테스트로 고정한다.

## 13. 사용량 제한과 남용 방지

- 회원은 `user_id`, 비회원은 익명 ID 쿠키로 센다. 둘 다 IP 해시를 함께 센다.
- 익명 ID는 첫 시도 때 Route Handler가 httpOnly 쿠키로 발급한다. Next.js 16의 `cookies()`는 비동기이고, 쿠키 쓰기는 Route Handler나 Server Function에서만 된다.
- IP 원문은 저장하지 않는다. 날마다 바뀌는 비밀값으로 해시한다.
- 제한은 요금제별 일일 시도, IP당 분당 5회, 전체 일일 예산 세 가지다.
- 확인과 차감은 DB 함수 하나로 원자적으로 처리한다. 동시 요청으로 한도를 넘지 않게 하려는 것이다.
- 날짜 경계는 Asia/Seoul 자정이다.
- 한도를 넘으면 429와 함께 다시 쓸 수 있는 시각과 대안을 돌려준다.

## 14. 계정

- Supabase Auth의 GitHub OAuth를 쓴다.
- 로그인 기능을 붙일 때 `src/proxy.ts`를 만들고 `updateSession()`으로 세션을 갱신한다. Next.js 16에서 Middleware는 Proxy로 이름이 바뀌었다.
- Proxy는 리다이렉트 같은 낙관적 확인만 한다. 권한은 서버 코드와 RLS에서 다시 확인한다.
- 가입하면 이 기기의 복습 기록과 오늘 사용량을 계정으로 합친다.
- 설정에서 계정을 지우면 시도와 복습, 신고와 대기 신청을 함께 지운다.

Supabase Postgres에 둔다. 테이블을 만들 때마다 마이그레이션을 만들고 `npm run db:types`로 타입을 갱신한다.

- 회원의 답변 원문은 기록 화면을 위해 저장한다. 비회원 답변은 저장하지 않고 해시만 남긴다.
- 비회원이 피드백과 꼬리 질문을 요청할 때는 클라이언트가 답변을 다시 보낸다. 서버는 해시가 맞는지 확인한다.
- 판정 신고에 답변을 포함할지는 사용자가 고른다.
- Pro 대기 신청은 로그인한 사용자만 할 수 있다. 이메일을 따로 받지 않는다.
- RLS: 회원은 자기 행만 읽는다. 쓰기는 서버에서만 한다. `usage_daily`와 `llm_calls`는 서버 전용이다.
- 보관 기간: 비회원 시도 30일, `llm_calls` 90일. 회원 데이터는 계정 삭제 때 지운다.

### 16.2 렌더링 경계

- 공개 페이지는 서버 컴포넌트로 정적 생성한다. 질문 상세의 연습 패널만 클라이언트 컴포넌트다.
- 대시보드는 로그인 정보가 필요해서 요청 때 렌더링한다.
- 스트림은 Route Handler가 `ReadableStream`으로 돌려준다. POST Route Handler는 캐시되지 않는다.
- 이 기기의 복습 목록은 홈에서 클라이언트 컴포넌트로 읽는다.
- JSON-LD는 page에 `<script type="application/ld+json">`로 넣고 `<`를 이스케이프한다. MVP에는 BreadcrumbList만 넣는다. 다른 타입은 화면 내용과 맞는지 확인한 뒤 추가한다.

| `follow_up_answered`  | `slug`, `index`, `covered`, `total`  |
| `self_rated`          | `slug`, `rating`                     |
| `review_started`      | `due_count`                          |
| `limit_reached`       | `plan`, `kind`                       |
| `judgment_reported`   | `slug`, `reason`                     |
| `signup_completed`    | `provider`                           |
| `pricing_viewed`      | `source`                             |
| `pro_waitlist_joined` | 없음                                 |

- 이벤트는 구현할 때 `analytics.ts`의 `AnalyticsEvents`에 먼저 추가한다.
- 답변 원문, 이메일, 사용자가 쓴 글은 이벤트에 싣지 않는다.
- 리렌더링으로 같은 이벤트가 두 번 가지 않게 한다.
- 퍼널과 리텐션은 PostHog로 본다. 지금 연결된 Vercel Analytics는 커스텀 이벤트를 Pro 플랜부터 집계한다.

### 17.3 핵심 지표

- 답변 제출률: `answer_submitted` / `question_viewed`
- 해설 먼저 보기 비율: 낮을수록 4.1 원칙이 지켜진다.
- 피드백 완료율과 자가 평가 비율
- 가입 전환율
- D1, D7 복습 복귀율
- 판정 신고율
- Pro 대기 신청률
- 시도당 AI 비용

### 17.4 A/B 실험 (P1)

- 피드백 형식: 체크리스트 먼저 대 문장 먼저
- 익명 ID 해시로 배정하고 노출을 기록한다.
- 주 지표는 자가 평가까지 간 비율이다.
- 트래픽이 적어 통계적 유의성은 기대하지 않는다. 정성 피드백과 함께 해석한다.

## 18. 테스트 전략

### 18.1 단위 테스트

- 콘텐츠 스키마
  - 모든 질문이 스키마를 통과한다.
  - slug와 핵심 포인트 ID가 겹치지 않는다.
  - 꼬리 질문이 가리키는 핵심 포인트가 있다.
  - 공개 기준을 채운다.
- 판정 후처리: 모르는 ID 제거, 빠진 포인트 채우기, 근거 문장 검증
- 꼬리 질문 선택 규칙
- 간격 반복 계산과 날짜 경계
- 사용량 제한 판단: 요금제별 한도, 날짜 경계, 예산 상한
- 프롬프트 조립: 구분자, 핵심 포인트 포함, 답변 속 지시문 격리
- 입력 검증: 답변 길이와 존재하지 않는 slug, 카테고리

### 18.2 E2E

`LLM_MODE=mock`으로 돈다.

1. 홈 -> 카테고리 -> 질문 상세
2. 답변 제출 -> 판정 표시 -> 피드백 스트림 완료
3. 꼬리 질문 답변 -> 판정 표시
4. 자가 평가 -> 다음 복습 날짜 표시 -> 홈의 오늘의 복습에 반영
5. AI 오류 -> 자가 점검으로 전환
6. 사용량 소진 안내
7. 질문 페이지의 제목, canonical, OG 메타데이터
8. 없는 질문 slug -> 404

로그인 이후 흐름은 Supabase 로컬 환경과 테스트 사용자로 검증한다. 방법은 계정 기능을 만들 때 정한다.

### 18.3 CI

- 기존 워크플로를 그대로 쓴다. 콘텐츠 검증이 단위 테스트에 들어 있어서 잘못된 콘텐츠는 PR에서 막힌다.
- 품질 평가 세트는 CI에서 돌리지 않는다.

## 19. 접근성과 화면 상태

- 스트리밍 중인 피드백 영역에 `aria-busy`를 둔다. 끝나면 완료 사실을 `aria-live` 영역으로 한 번 알린다.
- 판정 결과가 나오면 결과 제목으로 포커스를 옮긴다.
- 모든 버튼과 입력란에 레이블을 단다. 키보드만으로 연습 흐름을 끝낼 수 있어야 한다.
- 높이는 `dvh`를 쓰고 하단 고정 버튼에는 `pb-safe`를 붙인다.
- 로딩, 빈 목록, 오류, 사용량 소진 상태를 모두 화면으로 만든다.

## 20. 일정

### 1주 차: AI 없는 1차 공개

- 콘텐츠 스키마와 질문 10개
- 공개 페이지와 sitemap, OG 이미지
- 자가 점검 연습과 간격 반복. 기록은 이 기기에 저장한다.
- E2E와 콘텐츠 검증
- 배포. 공개 조건은 질문 10개와 핵심 흐름 E2E 통과다.

### 2주 차: AI 피드백

- Supabase 테이블과 마이그레이션
- 판정과 피드백 스트림, 꼬리 질문과 모의 모드
- 사용량 제한, 비용 기록, 킬 스위치
- 계측 이벤트와 소개, 개인정보 처리방침
- 질문 21개와 품질 평가 세트 30개 사례
- 시도당 비용을 재고 요금제 숫자 확정

### 3주 차: SaaS와 MVP 공개

- GitHub 로그인과 기록 합치기, 대시보드와 계정 삭제
- 요금제 페이지와 Pro 대기 신청
- 판정 신고
- 접근성 점검과 모바일 QA
- MVP 공개와 사용자 피드백 수집

투입 시간이 부족하면 P0 범위는 유지하고 날짜를 미룬다.

## 21. 출시 기준

- 공개 질문이 카테고리마다 3개 이상이고 모두 출처와 확인일이 있다.
- AI 판정이 품질 평가 세트에서 기준 이상 일치한다. 기준은 첫 측정 뒤 정한다.
- AI를 꺼도 자가 점검으로 학습 흐름이 끝까지 간다.
- 사용량 제한과 전체 예산 상한이 서버에서 동작한다.
- 질문 페이지의 메타데이터와 canonical, OG 이미지와 sitemap을 확인했다.
- CI가 통과한다.
- 이벤트가 중복이나 누락 없이 들어온다.
- 개인정보 처리방침에 저장 항목, 보관 기간, AI 제공자 전송 사실을 적었다.

## 22. 가설과 검증

### 가설 A

읽기보다 직접 설명하고 피드백을 받는 연습이 더 오래 기억에 남는다.

검증: 복습 때 같은 질문에서 충족한 포인트 수가 늘었는지 본다. 사용자 인터뷰를 함께 한다.

### 가설 B

사람이 쓴 핵심 포인트에 근거한 판정은 사용자가 믿고 쓴다.

검증: 판정 신고율과 정성 피드백을 본다.

### 가설 C

꼬리 질문은 실제 면접 대비에 도움이 된다고 느낀다.

검증: 꼬리 질문 응답률과 인터뷰를 본다.

### 가설 D

공개 질문 페이지는 검색 유입의 기반이 될 수 있다.

검증: 색인 상태, 검색 노출, 자연 검색 유입을 본다. 초기 데이터가 적을 때 성과를 단정하지 않는다.

### 가설 E

무료 사용량을 다 쓴 사용자 중 일부는 Pro에 관심을 보인다.

검증: `limit_reached` 이후 `pricing_viewed`와 `pro_waitlist_joined` 비율을 본다.

## 24. 결정 필요 사항

1. 서비스 이름: 작업명은 꼬리질문이다. 바꾸면 `src/config/site.ts`와 문서, `package.json`과 `supabase/config.toml`을 함께 바꾼다. GitHub 저장소 이름도 맞춘다.
2. 모델과 비용: 기본은 `claude-opus-5-5`다. 2026-10-06 기준 단가는 100만 토큰당 입력 4달러, 출력 20달러다. `claude-haiku-5-5`는 입력 0.10달러, 출력 0.50달러다. 바꿀지는 품질 평가 세트로 비교한 뒤 정한다.
3. 요금제 숫자: 2주 차 비용 측정 뒤 확정한다.
4. 결제: 토스페이먼츠 테스트 모드로 정기 결제를 테스트할 수 있는지 확인한다.
5. Vercel 프로젝트: 연결할 때 이름을 kkori로 맞춘다.
6. 공개 도메인

## 25. MVP의 성공 정의

MVP의 성공은 질문 수나 기능 수로 판단하지 않는다.

- 만든 사람이 2주 이상 매일 쓴다.
- 만든 사람 외 실사용자 5명 이상이 서로 다른 날 3회 이상 연습한다.
- 사용자 피드백으로 제품을 한 번 이상 고친다.
- 공개 페이지와 CI, 계측과 사용량 제한이 실제 배포 환경에서 동작한다.

이 문서의 숫자와 가설은 운영 데이터에 따라 고친다.
